## 1. Ingest: what should not be stored

Rows per day and `raw` bytes on prod, last full days (2026-09-22 to
2026-09-25):

| Source | Rows/day | `raw` MB/day | Avg `raw` |
|---|---|---|---|
| `caddy_access` | 64,602 - 76,132 | 91 - 100 | 1,382 - 1,476 B |
| `caddy_error` | 2,967 - 3,378 | 0.7 - 0.8 | 244 B |
| `audit` | 1 - 4 | 0 | 225 B |

What the rows are:

| Family | Match | Rows (7 d) | Share | Per day | Note |
|---|---|---|---|---|---|
| Reverse-proxy active health checker | `caddy_error`, `logger = http.handlers.reverse_proxy.health_checker.active`, message `HTTP request failed` | 20,147 | 93 % of `caddy_error` | 2,880 (one every 30 s) | one backend probed every 30 s that keeps failing; 9 more rows in the same logger say `host is unhealthy` / `host is up`, those are the transitions worth keeping |
| AppSec unavailable | `caddy_error`, `logger = crowdsec.appsec` | 889 | 4 % | 12 - 378 | see section 6; these must stay |
| Uptime-Kuma | `caddy_access`, `user_agent LIKE 'Uptime-Kuma/%'` | 140,308 | 29 % of `caddy_access` | 20,400 (14 hosts x 1/min), 22 MB/day | paths `/` 200 / 302, `/public` 301 |
| UptimeRobot | `user_agent LIKE '%UptimeRobot/%'` | 1,979 | 0.4 % | 280 | |
| Home Assistant camera proxy | `path LIKE '/api/camera_proxy/%'` on one host, tablet user agent | 241,915 | 50 % | 34,500 | legitimate app traffic (MJPEG polling); it is why the 500k cap is reached in 7 days |
| Googlebot | `user_agent LIKE '%Googlebot/%'` | 10,467 | 2 % | 1,500 | legitimate |

How to filter, where: the ingestor already parses every line into
a `models.LogEntry` and passes it to the observer (`LogWatcher`,
which turns the health-checker lines into target up/down events
and the WAF lines into bursts) before the writer. The filter goes
**between the observer and the writer**: the watcher keeps seeing
every line, the table does not. Rules, settings-driven with these
defaults:

- `logs.ingest.drop_loggers`: `http.handlers.reverse_proxy.health_checker.active`
  when the message is the routine `HTTP request failed` (the
  `host is unhealthy` / `host is up` transitions are kept).
- `logs.ingest.drop_user_agents`: prefixes `Uptime-Kuma/`,
  `UptimeRobot/` (the operator can add more).
- `logs.ingest.drop_paths`: empty by default; the camera proxy is
  the operator's call (it is real traffic, and it is 50 % of rows).

Savings with the defaults: 2,880 + 20,700 = **23,600 rows/day
(31 % of all rows) and 22.8 MB/day of `raw`**; the 500k cap would
then hold about 10 days instead of 7. Honesty: the dashboard
"Requests (24 h)" card drops by 29 % the day this ships. The
ingestor keeps per-rule drop counters (`/api/logs/ingest-stats`),
the overview card carries "excluding monitors" and the release note
says the number changed and why. The retention purge does not touch
the filter: rows already stored stay until their retention.

## 2. Retention and the purge

Current: `logs.retention_days=30` (global, never reached),
`logs.max_entries=500000` (reached: oldest row 2026-09-19, seven
days), purge every 6 h plus one 120 s after boot (v1.3.38.3),
batched 5,000 rows / 100 ms; before the cap check the purge runs
`SELECT COUNT(*) FROM log_entries` (a full index walk of 500k rows,
0.3-1 s on prod, on the single connection). `raw` averages 1,457 B
on access rows: about 700 MB of the 1,267 MB table is the JSON copy
of a line whose useful fields are already in columns.

Proposal (no schema):

| Source | Rows kept | `raw` kept |
|---|---|---|
| `caddy_access` | 7 days | 24 h, then `raw = NULL` |
| `caddy_error` | 30 days | 30 days (244 B, it is the message) |
| `audit` | 90 days | 90 days |
| `waf_audit` | 30 days | 30 days |

- `logs.retention.<source>_days` settings with those defaults;
  `logs.retention_days` kept as the fallback for unknown sources.
- Purge per source: `DELETE ... WHERE source = ? AND timestamp < ?`
  batched, on `idx_log_entries_source_ts`.
- `raw` strip: `UPDATE log_entries SET raw = NULL WHERE source =
  'caddy_access' AND raw IS NOT NULL AND timestamp < now-24h`,
  batched 5,000 rows like the purge, same ticker. What the Logs
  page loses for rows older than 24 h: the "raw" panel of the row
  detail and `q` matches inside `raw`; every column stays.
- The count: ids are monotonic and the purge always deletes the
  oldest, so `MAX(id) - MIN(id) + 1` is the exact row count in two
  primary-key lookups. The `max_entries` cap stays as a safety at
  1,000,000.
- Expected table after 7 days at today's traffic with 1 + 2: rows
  about 340k (48k/day x 7), `raw` only on the newest 24 h
  (about 70 MB), table around 250-300 MB instead of 1,267 MB; the
  six indexes shrink with the rows. Real numbers after the first
  full retention cycle, in the 40.0 release note.

## 3. Hourly rollup (migration 034)

What the long ranges need today (`dashboard.Queries.Traffic`,
`db.ComputeStats`, `db.ComputeTimeseries`, `dashboard/overview`):
requests per bucket by status class, p50 / p95 / p99 of
`duration_ms` per bucket, `bandwidth_out_bytes`, top hosts, top
paths, `logs/stats` avg and p95 and by-source counts. v1.3.38.4
serves the counts from covering indexes and everything that needs
`duration_ms`, `size_bytes` or `path` from the newest 24 h only
(`detail_window`, `series_covers_range`, `sample_n`).

Table:

```sql
CREATE TABLE log_hourly (
  hour          TIMESTAMP NOT NULL,   -- UTC hour start
  source        TEXT      NOT NULL,
  host_id       INTEGER,              -- NULL = no host (errors, audit)
  status_class  INTEGER   NOT NULL,   -- 2,3,4,5; 0 = no status
  requests      INTEGER   NOT NULL,
  bytes_out     INTEGER   NOT NULL DEFAULT 0,
  dur_sum_ms    INTEGER   NOT NULL DEFAULT 0,
  dur_max_ms    INTEGER   NOT NULL DEFAULT 0,
  dur_p50_ms    INTEGER,  dur_p95_ms INTEGER, dur_p99_ms INTEGER,  -- exact for the hour
  dur_h0 INTEGER NOT NULL DEFAULT 0, dur_h1 INTEGER NOT NULL DEFAULT 0,  -- histogram:
  dur_h2 INTEGER NOT NULL DEFAULT 0, dur_h3 INTEGER NOT NULL DEFAULT 0,  -- <=50,<=100,
  dur_h4 INTEGER NOT NULL DEFAULT 0, dur_h5 INTEGER NOT NULL DEFAULT 0,  -- <=250,<=500,
  dur_h6 INTEGER NOT NULL DEFAULT 0, dur_h7 INTEGER NOT NULL DEFAULT 0,  -- <=1000,<=2500,<=5000,>5000 ms
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (hour, source, host_id, status_class)
);
CREATE TABLE log_hourly_paths (
  hour TIMESTAMP NOT NULL, host_id INTEGER, path TEXT NOT NULL,
  requests INTEGER NOT NULL, bytes_out INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (hour, host_id, path)
);
CREATE INDEX idx_log_hourly_source_hour ON log_hourly (source, hour);
CREATE INDEX idx_log_hourly_paths_hour ON log_hourly_paths (hour);
```

- Percentiles: the per-hour p50 / p95 / p99 are exact (the hour's
  durations sorted at fill time, 3,000 rows); the 7 d chart's
  hourly buckets use them as they are. A range-wide p95 (the
  `logs/stats` card) comes from the summed histogram, linear
  inside the bucket, labelled "from histogram". No `sample_n`.
- Top paths: the 50 busiest paths per host per hour, summed over
  the range (a path outside a host's hourly top 50 can only be
  missing from a range top 10 if it never made any hour's top 50;
  acceptable, and labelled).
- Fill: a job at HH:02 aggregates [HH-1, HH) from `log_entries`
  (counts from the covering indexes; one pass over the hour's rows
  for durations, bytes and paths; about 3,000 access rows, under
  0.3 s on prod) and `INSERT OR REPLACE`s the hour; idempotent, so
  the boot path re-runs it for every hour since `MAX(hour)` that is
  older than the newest `log_entries` row (missed hours after a
  panel outage). Ingest-time counting was rejected: it puts the
  rollup on the writer's hot path and needs the same hourly pass
  anyway for percentiles and paths.
- Backfill of what exists: 168 hours at about 0.3 s each, batched
  with the retention pauses, about a minute, run once by the boot
  path of 40.1 (it is the same "missing hours" loop).
- Rollup rows keep their own retention (`logs.rollup_days`, default
  90) so 30 d dashboards exist after 40.2 without touching
  `log_entries`.
- Writes: 4 status classes x 19 hosts + errors per hour, about 100
  rows/hour; negligible.

Endpoints that move to the rollup in 40.2: `dashboard/traffic` for
24 h and 7 d (completed hours from `log_hourly`, the current hour
live from `log_entries`, both stitched in Go; 1 h and 6 h stay
live at their 5 / 15 min granularity), `logs/stats` and
`logs/timeseries` when the filter is only time / source / host,
`dashboard/overview` 24 h counters, the Security overview's 24 h
Coraza counts stay on `log_entries` (small). The bridge fields
(`detail_window`, `detail_from`, `series_covers_range`, `sample_n`)
are emitted for one more release as `true` / empty and removed in
40.3. Range `30d` becomes possible (rollup only).

Migration 034 extends the `TestRollbackLastMigration` peel chain;
`down` drops the two tables. Schema-frozen note in `storage.md`
moves from 033 to 034.

## 4. Read pool

Why the pool is one connection: the first SQLite commit
(`5e0927c`, 2026-04-18) set `SetMaxOpenConns(1)` "to avoid
database is locked under contention"; `storage.md` documents it as
the single-writer choice and, in the same page, credits WAL for
"concurrent readers" that the pool never allows. The strikes record
WAL lock contention only in `:memory:` tests (each connection sees
its own database), which is a test-DSN matter, not the prod file.

Long readers on the single connection after items 1-3 ship:

| Reader | Today | After 40.0-40.2 |
|---|---|---|
| `logs?q=` (LIKE over `path`, `user_agent`, `message`, `raw`) | 24 h 1.9 s, 7 d 11.7 s | `raw` only on the newest 24 h: 7 d becomes about 24 h-of-raw plus columns, a few seconds at most |
| `logs/export.csv` | streams every row in range | unchanged; minutes on 7 d |
| `VACUUM` (monthly, day 1, 04 UTC) | holds the connection for the whole rewrite of 1.7 GB | 300 MB file: seconds to a minute |
| `VACUUM INTO` (nightly backup, 02:00 UTC) | holds it while the 128 MB copy is written | smaller, still seconds |
| retention purge / `raw` strip | batched 5,000 / 100 ms | same |
| dashboard / stats | cache + covering indexes + rollup | ms |

So the pool is not what makes the dashboard slow any more; it is
what makes an export or a `q` search stall every other request and
the ingestor for seconds. A reader pool is still the right fix for
those, and it is small: a second `*sql.DB` on the same file with
`mode=ro` and `_pragma=query_only(1)`, `SetMaxOpenConns(2)`, opened
after migrations, used by the GET handlers of logs, export, threats
and the dashboard loaders; the writer keeps its single connection.
Risks: a long read pins the WAL snapshot so checkpoints cannot
truncate past it (WAL grows during an export, shrinks after);
`busy_timeout` applies to readers too; nothing else changes. Gate:
the section 3.3 probe of the review (40 x `/api/hosts` every 250 ms
during a forced 7 d export, p99 < 50 ms). Recommendation: 40.3,
after 40.0-40.2 are measured, and only if that probe still fails
without it.

## 5. Bouncer: stream vs live

Why live: v1.3.20 (2026-04-25) set `enable_streaming: false`
because the plugin's stream store only indexes `Ip` and `Range`
decisions and the panel was emitting `scope=Country` bans
(`caddycfg.go` comment, v1.3.20 release note). v1.3.21, the next
day, found that live mode does not honour `Country` either
(`IPEquals` only) and moved country bans to panel-side `Range`
expansion, which the stream store does index. **The reason for
live mode disappeared in v1.3.21**; the comment's "the bouncer ships
an in-process cache that absorbs it" is not true of v0.12.1
(`internal/bouncer/live.go`: no cache).

What live mode costs on prod today (LAPI log, 30 min sample, 1,236
lookups):

| | Live (today) | Stream |
|---|---|---|
| LAPI calls | one `GET /v1/decisions?ip=` per proxied request, about 59,000/day | one pull per `ticker_interval` (15 s): 5,760/day, deltas after the first full pull |
| Latency on the request path | **avg 72 ms, max 100 ms** per request (crowdsec CPU-throttled, section 6) | none (in-memory lookup) |
| Ban applied after | immediately | within the ticker (15 s) |
| LAPI down | nothing enforced (fail-open, section "What happens if CrowdSec is down") | the last pulled set keeps applying; only bans issued during the outage are missed |
| Caddy memory | flat | the decision set: about 24k IPs + 10k ranges, a few MB |
| Config load | independent of the LAPI | `Init` builds the stream client; a reconcile push while the LAPI is down may fail: pre-flight |

Risks and the pre-flight for 40.3 (demo stack, then prod off-hours
with the operator): (1) a `Range` decision from a country expansion
blocks a request in stream mode (the store's radix tree with 10k
ranges, lookup cost); (2) full pull size and time with 24k
decisions, then delta pulls; (3) stop crowdsec for 60 s: bans keep
applying, then the bouncer resumes without a Caddy restart;
(4) push a Caddy config with the LAPI down; (5) a ban added by the
panel is enforced within 15 s. AppSec is unaffected (still per
request). If all five pass, stream mode ships as a setting
(`crowdsec.stream_mode`, default on for new installs, opt-in on
prod) with `docs/features/crowdsec.md` updated.

## 6. New finding: the crowdsec container is CPU-throttled a third of the time

`docker-compose.yml` caps crowdsec at `cpus: 0.5` (`cpu.max
50000 100000`). Its cgroup `cpu.stat` since the container started
(2026-09-13): `nr_periods 2,611,599`, `nr_throttled 810,383`
(**31 %**), `throttled_usec 72,790 s` (20.2 h) against
`usage_usec 58,623 s` of CPU used. Caddy, same cap: 681 throttled
periods of 5.2 M (0.01 %).

What it does on prod:

- AppSec `context deadline exceeded` (2 s `appsec_timeout`): 370
  requests in 8 days went through **uninspected** (fail-open);
  peaks at 01 UTC (190 of 889 errors in that hour across the
  period) and on 2026-09-21 / 2026-09-25 (288 and 378 lines). The
  nightly backup runs at 02:00 UTC and the retention purge every
  6 h; the 01 UTC peak is not explained by either yet. The other
  496 lines are `context canceled` (the client closed the
  connection while AppSec was evaluating; the camera streams fit).
- LAPI lookups at 72 ms average (the live bouncer, on the request
  path) where the LAPI itself answers the panel's queries in 5-30 ms.

Proposal, operator's decision, no code: `docker update --cpus 1
argos-prod-crowdsec` (no restart) and `CROWDSEC_CPU_LIMIT=1.0` in
the operational `.env` (same divergence note as the memory cap
until the alignment recreate), then re-read `cpu.stat` and count
`crowdsec.appsec` error lines after 24 h. The host has 2 vCPU; the
panel sits at 0.3 % and Caddy at 1 %, so the extra half core is
free most of the time. The measurement belongs in the 40.0 release
note either way.

### 6.2 The 01 UTC peak, correlated

It was one event, not a nightly pattern: 190 of the 889
`crowdsec.appsec` error lines are from **2026-09-21 01:52-01:53
UTC**, 188 of them `context canceled` (the client closed the
connection while AppSec was evaluating) and 2 timeouts; the access
rows of those two minutes are the tablet's camera-proxy polling
(48 requests) plus Uptime-Kuma. No other day has an 01 UTC bucket.

The 370 timeouts (`context deadline exceeded`, 2 s) cluster by
**day**, not by hour: 297 on 2026-09-25 (the day of five image
builds, the 7 d smokes and host load up to 9.7), the rest 5-24 per
day, daytime hours (18, 09, 16, 08 UTC). Tested and rejected as
causes: the panel's nightly `VACUUM INTO` at 02:00 UTC (no
timeouts in that hour), the retention purge (every 6 h from boot),
the CrowdSec community-blocklist update (every 2 h at :16, 15,000
decisions rewritten: 0 timeouts within +-5 min of any run), the
system journal (no entries around the peak; a Proxmox `vzdump`
would not show inside the guest anyway). The AppSec timeouts are a
host-CPU-pressure symptom under the 0.5-core cap; 6.1 removes the
cap half, the +24 h reading says whether the deploy-day pattern
survives.

### 4.1 Input from the v1.3.40.3 gate (2026-09-26): the hold per batch and the refresh stalls

Measured on prod, `/api/hosts` sampled from the host:

| Run | What held the connection | `/api/hosts` |
|---|---|---|
| v1.3.40.2 strip, 1,000-row batches, 80,653 rows, 109 s | about 180 ms per 1,000-row UPDATE (1.4 KB rows), 100 ms pause | p50 178 ms, p90 239 ms, p99 465 ms, max 689 ms (n=184) |
| v1.3.40.3 strip, 200-row batches, 666 rows, 1.86 s | 4 batches; one sample of 1,137 ms coincided with a pinned refresh | n=4, max 1,137 ms |
| v1.3.40.3 forced purges with 58 and 2 rows to strip | 0.33 s and 0.20 s total | one sample of 195 ms / 170 ms each |
| v1.3.40.3 smoke: purge with 214 rows to strip, 0.55 s | | n=3, p99 204 ms |
| **No purge at all, 120 s at 20 ms cadence** | the pinned warm-set refresh every 24 s (traffic 24 h, about 0.8 s cold) | p50 1.4 ms, p99 4.8 ms, **max 542 ms; 15 of 3,667 samples over 50 ms, every one within 1 s of a refresh** |

Reading: with 200-row batches the strip's own hold is about 40 ms
and no longer decides the gate; the single connection does. Any
request that arrives while the pinned traffic refresh runs waits
up to 0.5 s, every 24 s, purge or not, and a purge that lasts more
than a few seconds always overlaps one. The 50 ms p99 gate during
a purge is therefore unattainable with one connection, whatever
the batch size.

Decision (operator's rule of 2026-09-26): the batch is not lowered
below 200; **the read pool (item 6) moves from 40.3 to 40.1**, with
its pre-flight on the dense demo seed (the seed itself, section 6.1
of the CHANGELOG known issues, comes first). The rollup (migration
034) moves to 40.2 and the endpoint switch to 40.3. Gate for the
pool, unchanged from section 4: `/api/hosts` p99 < 50 ms during a
forced 7 d export and during a purge that strips 50k rows on the
dense seed, then on prod.

### 8.2 Findings that change the 40.1 scope

1. **The strip cursor query rescans from the oldest row on every
   batch.** `stripRawByCursor` filters with
   `timestamp < cutoff AND (timestamp > cur OR (timestamp = cur AND id > curId))`.
   With the lower bound inside an OR the planner (SQLite 3.46 in
   modernc) uses only `timestamp < ?` on `idx_log_entries_source_ts`
   and walks the index from the oldest row until it has 200 matches:
   100 to 150 ms of CPU per batch at 400k rows, growing as the cursor
   advances. The sqlite3 CLI (3.45) picks both bounds for the same
   text, which is why the probe with literals looked fine. Rewritten
   as `timestamp >= cur AND timestamp < cutoff AND NOT (timestamp = cur AND id <= curId)`
   the plan is `source=? AND timestamp>? AND timestamp<?` and the
   SELECT takes 0.4 ms. The full strip drops from 392 s to 242 s and
   the panel CPU during it from 55 % to 5 %. This is what the 40.3
   gate on prod was measuring (p99 241 ms at 1,000 rows, then 200
   rows); the batch size was never the problem.
2. **Every authenticated request reads the session on the writer
   handle.** `Authenticate` calls `session.Lookup` with `h.DB`, so
   with the read pool in place `/api/hosts` still stalled 0.2 to
   1.4 s once per checkpoint while the strip ran under IO pressure
   (the writer connection is busy for the whole checkpoint fsync).
   Moving the lookup to the read handle (Touch stays on the writer,
   one UPDATE per 5 min) removed the stall: p99 5.5 ms over the whole
   430k strip.
3. **Checkpoint fsync under IO pressure is what a single connection
   exposes.** With `synchronous=NORMAL` the WAL autocheckpoint (every
   4 MB, about every 1.5 s during a strip) writes 1,000 pages and
   fsyncs the DB file; on this disk that took 0.2 to 1.4 s while
   `/proc/pressure/io` avg10 sat at 10 to 14 %. Anything queued on
   the writer connection waits that long. The read pool is the fix
   for readers; the writer keeps paying it (ingest batches, PUTs).
4. **Panel memory and CPU caps.** The panel cgroup is 512 MB and
   1 CPU on prod and demo; the page cache counts against the cap, so
   a 1.3 GB DB never fits (prod file 1.72 GB) and `memory.peak` sits
   at the cap during a strip without an OOM. Raising the demo cap to
   1.5 GB did not change the strip gate (p99 282 ms with the old
   cursor), so the cap is not the lever. Go 1.25 sets GOMAXPROCS from
   the cgroup CPU limit, so the panel runs one P; a 2-CPU cap did not
   change the export gate either.
5. **Handler inventory** (80 GET routes): all read-only except
   `OIDCCallback` (user upsert + session create) and `ForwardAuth`
   (session touch); `h.audit` only queues (the ingestor writes);
   several GETs read through components that hold the writer
   (`DashQueries`, `NotifRepo`, `BackupMgr`, country jobs, appsec
   status, public IP, timeout cache). No GET opens a transaction; the
   CSV export pages with LIMIT/OFFSET (no snapshot) and the SSE
   stream polls once a second.

Read-only pass on the dense demo with a probe binary (not committed)

### 9.1 What the rollup serves and what stays on raw

Two facts from the inventory bound the design:

- Only the 7 d dashboard range uses hourly buckets. 1 h, 6 h and
  24 h series use 1, 5 and 15 min buckets (`dashboard/range.go`), so
  the rollup cannot serve those series; it serves the 7 d and the new
  30 d series, and the 24 h **totals** (overview counters, `logs/stats`
  cards) as closed hours plus the live edges.
- Every consumer's window ends at "now" (the Logs page sends only
  `from`), so every rollup read is stitched in Go: closed hours from
  `log_hourly`, the hour in progress (and the partial hour at the
  window start) from `log_entries` with the existing queries.

| Consumer field | Source in 42.0 | Note |
|---|---|---|
| 7 d / 30 d series per status class (`classSeriesSQL`) | `log_hourly` `requests` by `status_class` | exact |
| 7 d / 30 d top hosts by requests (`topHostsByIDSQL`) | `log_hourly` summed by `host_id` | exact |
| bandwidth, requests, 5xx / 403 / 429 counts over 24 h, 7 d, 30 d | `log_hourly` `bytes_out`, `requests`, `status_class`; 429 needs its own column (`rate_limited`), added | 403 and 429 share class 4, so `rate_limited` and `forbidden` counters are added to the table |
| 7 d response-time series (p50 / p95 / p99 per hour) | `log_hourly` `dur_p50/95/99_ms` per hour, merged across groups by the histogram | per-group exact; the per-hour value across hosts and classes comes from the summed histogram, labelled |
| `logs/stats` avg and p95 for windows over 24 h | `dur_sum_ms / requests` and the summed histogram | today: newest 20,000 rows sample; the rollup is closer to the truth |
| 7 d top paths (`top paths`, `topN`) | `log_hourly_paths` top 50 per host per hour, summed | a path can only be missing from a range top 10 if it never made an hourly top 50; labelled |

| 30 d range | rollup only | new |

Stays on raw rows, by design ("solo raw"):

- Everything with 1 / 5 / 15 min buckets (1 h, 6 h, 24 h series and
  response times, Security detected / blocked series).
- Any filter beyond time, source and host: status expression,
  method, path substring or regex, `remote_ip`, level, free-text
  `q`, `rule_id`, WAF fields. `logs/stats` with those filters keeps
  the row path (already bounded by v1.3.38.4).
- Every WAF (`waf_audit`) query: attack types, attacking IPs and
  countries, attacked paths, per-host WAF stats (distinct IPs and
  `MIN(waf_rule_message)` are not rollup shapes; the source is
  small).
- Rows: log list, detail, export, SSE stream, recent errors, audit
  log, health-checker events, cert events, log shape.

### 9.2 Schema adjustments from the review

Against the section 3 draft: `host_id` becomes `NOT NULL DEFAULT 0`
(0 = no host) because a NULL inside a PRIMARY KEY never matches
itself in SQLite and `INSERT OR REPLACE` would append duplicates;
two counters are added, `forbidden` (status 403) and `rate_limited`
(status 429), because the security cards read them and class 4 hides
them; `errors` (rows with `level = error`) for the error source. The
`created_at` / `updated_at` columns stay (convention). Index names
are new (`idx_log_hourly_source_hour`, `idx_log_hourly_paths_hour`);
the migration creates two tables and two indexes and touches nothing
on `log_entries`, so the four load-bearing indexes
(`idx_log_entries_status_ts`, `_host_ts`, `_source_ts`,
`_timestamp`) are untouched (item 5).

### 9.3 Backfill of 168 h on the dense demo (strike 13 gate)

### 9.4 Fill job, recovery and divergence detection

- Job at HH:02 aggregates `[HH-1, HH)`; idempotent (`INSERT OR
  REPLACE` per key inside one transaction), so re-running an hour
  is safe.
- Recovery: at boot and at every tick the job fills every hour from
  `MAX(hour) + 1 h` in `log_hourly` (or `MIN(timestamp)` of
  `log_entries` when the table is empty) up to the last closed hour,
  behind the 100 ms pause. A lost tick (restart, purge running,
  panel down for a day) is repaired by the next tick or the next
  boot; the backfill of section 9.3 is the same loop.
- The hour in progress is never written; readers stitch it live.
- Divergence: `scripts/smoke/rollup-agree.sh` picks a closed hour
  at least 2 h old, runs `COUNT(*)`, `SUM(size_bytes)` and the per
  status-class counts on `log_entries` and compares with
  `SUM(requests)`, `SUM(bytes_out)` and the class rows in
  `log_hourly` for that hour: tolerance 0. It also asserts that the
  newest closed hour is present (the job ran). A drift check every
  6 h in the retention ticker re-runs the same comparison for the
  newest closed hour and logs `rollup drift` with both numbers;
  `logs/pipeline` exposes `rollup.last_hour`, `rollup.last_run_at`
  and `rollup.drift`.
- Retention: `logs.rollup_days` (default 90) purged by the same
  ticker; the strip and cap purges never touch the rollup.

### 9.5 Migration 034 and the way back

- `034_log_hourly.up.sql` creates the two tables and two indexes;
  `034_log_hourly.down.sql` drops them (convention: every migration
  has a `.down.sql`; `argos migrate rollback` runs the newest one).
  `TestRollbackLastMigration` gets a 034 peel step at the top that
  asserts both tables are gone.
- Deploy procedure: `POST /api/backups` (VACUUM INTO) before
  `make deploy-prod`, recorded in the release notes; the 42.0 boot
  runs the migration and then the backfill behind the pause.
- Way back to v1.3.41.1 (documented before the up is written):
  repin 1.3.41.1 in `~/argos-prod` and `make deploy-prod`; 41.1
  ignores the two tables, so the DB needs nothing; optionally
  `docker compose exec argos /argos migrate rollback` drops them
  (only after the repin, since the 42.0 boot would recreate them).
  The backup is the last resort, restored through
  `argos restore --file ... --yes` and a restart.
