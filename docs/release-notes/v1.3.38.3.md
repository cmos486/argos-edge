# v1.3.38.3 -- Boot path, certs list, deterministic test, one TLS probe

Fourth release of the v1.3.38 series ("dashboard paints in under a
second"; scope in `docs/operations/ux-performance-review.md`). Four
items in the order the operator set. No schema change.
`argosVersion` `1.3.38.2` -> `1.3.38.3`.

## 1. Boot path

PHASE 0 came from the 1.3.38.2 container's own boot log rather
than a restart of prod:

| Phase | Time from `argos starting` |
|---|---|
| migrations | < 10 ms (before the marker) |
| caddy probe, ingestor, geoip loaded | +0.02 s |
| boot retention purge holds the single SQLite connection (DELETE by age + `COUNT(*)` over 500k rows + DELETE by cap; 2,101 rows) while backup reconcile and caddy reconcile queue behind it | +0.02 s to +1.53 s |
| `retention purge done`, `caddy reconcile ok` | +1.65 s |
| `http listening` | **+1.75 s** |

Two facts changed the plan: the panel container runs with
`cpus: 1.0`, so its boot cannot produce host load above 1, and the
9.7 load spike of a deploy starts ~30 s before the container
exists (7.3 at 20:06:32 for a 20:07:00 start), i.e. in the build's
final phase and the recreate. The boot fix is therefore about the
DB connection, not CPU:

- `logs.BootPurgeDelay = 2 min`: the first purge runs two minutes
  after `StartRetention` (listen follows it within a second), then
  every 6 h as before.
- `db.PurgeOld` deletes in batches of `PurgeBatchSize` (5,000) with
  `PurgeBatchPause` (100 ms) between them, for both the age DELETE
  and the cap DELETE, at boot and on every tick and for
  `POST /api/logs/purge`. The longest single statement is now one
  batch.

Expected after: boot-to-listen ~0.3 s; first purge logged ~2 min
after listen. `scripts/smoke/panel-boot.sh` asserts both from the
boot log without restarting anything.

The deploy-tail spike is measured per process during this
release's deploy (`top -b` every 5 s); see "Deploy" below.

## 2. `/api/certs`

PHASE 0 on a `.backup` copy of prod (deleted after): every one of
the 21,681 `caddy_error` rows had `host_id` NULL and `host_domain`
empty, because `fillError` only read an `identifier` field that
this Caddy's error lines never carry (93 % are
`health_checker.active`; the rest have the domain under
`request.host`). Options measured:

| Option | Cost | Verdict |
|---|---|---|
| as shipped: `LOWER(message) LIKE`, 19 sequential queries | 0.04-0.07 s each warm; 0.93-1.6 s per list call | replaced |
| `host_id` + `idx_log_entries_host_ts` | 0.59 s (host 1), 7.07 s (busiest host): no error rows carry `host_id`, the index walk scans the host's access rows | rejected |
| `host_domain` grouped | 0.034 s but 0 matches (column empty) | needs C |
| B: no enrichment in the list, on demand per row | list ~ms; one bounded lookup per click | shipped |
| C: attribute `host_domain` at ingest | future rows indexable | shipped |

Shipped B + C:

- `ListCerts` returns rows without `last_renewal_event`.
- `GET /api/certs/{id}/last-event` -> `{host_id, domain, event |
  null, matched_by: "host_domain" | "message" | "", window: "720h"}`.
  Lookup 1: `source='caddy_error' AND timestamp >= now-30d AND
  host_domain = ?` (A2, index range on `(source, timestamp)`).
  Lookup 2 (only when 1 is empty): same bounded slice with a
  substring match on `message`, for rows that predate C.
- `fillError`: `identifier` -> `identifiers[0]` -> `request.host`
  (port stripped, lowercased). Old rows keep an empty `host_domain`
  and leave with retention.
- Certificates table: the "Last event" column stays; each row has a
  `show` button -> `loading...` -> the event link, `none (30d)`, or
  `failed, retry`. No page redesign.

## 3. Deterministic mutex test

`fakeLAPI` gained `gate` / `entered` channels: with `gate` set, every
`AddRangeDecisions` sends on `entered` and then blocks until `gate`
is closed (or the context ends). `TestSubmit_serialisesViaMutex`
submits two jobs, waits on `entered`, asserts that at that instant
exactly one job is running and the other pending (Submit does not
promise which of two back-to-back jobs wins the mutex; it promises
one at a time), closes the gate, and waits for both to complete. The 250 ms `addDelay` and the 400 ms sampling window
are gone from this test (`addDelay` stays for other tests).
`jobs.go` untouched.

## 4. One TLS probe

`internal/certprobe`: `Probe` (the SNI dial, formerly
`api.probeCert`) and `Cache` (formerly `api.CertProbeCache`), with
the same five tests. `internal/api`, `internal/server`, `main.go`
and `internal/notifications` use it; `CertAndDetectCron` takes a
`Probes *certprobe.Cache` instead of `CaddyTLSDial` and its 20-line
copy of the dial is deleted. `main.go` builds one cache before the
cron and hands the same instance to the HTTP handlers.
