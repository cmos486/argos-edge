## What ships

- `db.RawStripBatch` 1,000 -> 200: about 40 ms held per batch, then
  the 100 ms pause; 48k rows (6 h of access traffic) in about 35 s
  of light contention.
- `logs.DefaultMaxEntries` 500,000 -> 1,000,000; the same value set
  on prod. The cap is a safety net above what retention keeps, so
  the purge's `MAX(id)-MIN(id)+1` bound stays under it and no
  `COUNT(*)` runs.
- `logs-pipeline.sh`: the purge-path p99 and the strip are reported
  as separate checks naming which path ran.

## Gate and the item-4 input

After deploy: `raw_hours = 24`, kill-switch watcher armed at the
`POST /api/logs/purge` (not before, to skip boot noise), 50 ms p99
per 30 s window. Whatever the result, the hold per 200-row batch is
the input to item 4 of the v1.3.40 plan: if the gate still fails
with 200, the batch is not lowered further and the read pool moves
from 40.3 to 40.1 with its pre-flight on the dense demo seed.
