# v1.3.41.1 -- CSV export by keyset, streamed, paced

`argosVersion` `1.3.41.0` -> `1.3.41.1`. The v1.3.41.0 gate 3 (three
back-to-back 24 h CSV exports with `/api/hosts` p99 <= 50 ms) failed
on prod for a CPU reason: the export held the panel at 99-102 % of
its 1-CPU cgroup and every request that landed in that window
stalled. This release changes how the export walks and paces the
match set; `ARGOS_CPU_LIMIT` stays at 1.

## What ships

- `db.ListLogEntriesAfter`: the export walks the match set by a
  `(timestamp, id)` keyset instead of `LIMIT/OFFSET`. Each OFFSET page
  re-read every earlier row, so a 66k-row export visited about 1.1 M
  index entries; the keyset cursor uses both bounds as range terms
  (strike 14 rule) and `TestListLogEntriesAfterPlan` pins the plan.
  `TestListLogEntriesAfterWalksEveryRowOnce` covers rows that share a
  timestamp and the filter.
- `ExportLogsCSV` flushes the CSV writer and the HTTP response after
  every page (the client streams, the encoder holds one page) and
  pauses `exportPagePause` (20 ms) after each page of
  `exportPageRows` (500).
- The pause is the yield that works. `runtime.Gosched()` was tried
  first: with the keyset alone the export dropped from 5.5 s to
  1.5 s and the kernel throttled the container in 14 of 16 scheduler
  periods (155 ms) during that export; gate 3 still failed (p99
  88 ms with the pool on, 240 ms off). A sleep between pages keeps
  the duty cycle low: 0 of 36 periods throttled during a 3.5 s
  export at 1,000 rows per page, and the 500-row page halves the
  burst a request can land in.

## Measured on the dense demo (500k rows, 24 h export of 66k access rows, no IO pressure)

`/api/hosts` sampled every 100 ms across three exports; panel CPU
from `docker stats`.

| build | pool | export wall time | p50 | p95 | p99 | max | > 50 ms |
|---|---|---|---|---|---|---|---|
| v1.3.41.0 (OFFSET, no pause) | on | 5.5 / 7.2 / 5.7 s | 2.0 ms | 7.2 ms | 506 ms | 825 ms | 5 / 186 |
| v1.3.41.0 | off | 5.9 / 5.5 / 5.4 s | 44.4 ms | 249 ms | 395 ms | 483 ms | 56 / 121 |

| **v1.3.41.1** (keyset, 500 rows + 20 ms pause), run a | on | 5.3 / 5.4 / 5.2 s | 1.6 ms | 5.7 ms | **9.8 ms** | 85 ms | 1 / 186 |
| v1.3.41.1, run b | on | 5.2 / 6.4 / 5.2 s | 1.5 ms | 16.0 ms | 67.7 ms | 88 ms | 3 / 192 |
| v1.3.41.1 | off | 5.6 / 5.5 / 5.4 s | 1.9 ms | 24.2 ms | **38.2 ms** | 340 ms | 2 / 180 |

Reading the table:

- The export's own share is gone: with the pool off, where every
  read still queues on the writer, p95 fell from 249 ms to 24 ms and
  p99 from 395 ms to 38 ms. The two 300 ms samples left in the off
  column sit together at one instant and are the pinned dashboard
  refresh holding the writer, which is the pool's job, not the
  export's.
- With the pool on, run a passes with p99 9.8 ms. Run b fails on a
  cluster of three samples (68-88 ms) inside its slow export 2 (6.4 s)
  while `docker stats` read 101 %: the pinned 24 h refresh (a 1-2 s
  query at full CPU on the dense demo, 0.8 s on prod) landed on top
  of the export and the sum crossed the 1-CPU quota. The export alone
  no longer throttles the container.
- Wall time: 5.3 s, the same as v1.3.41.0's, because the pause
  gives back what the keyset saved; the difference is that the
  encoder now uses about a third of the quota instead of all of it.

## Gate on prod

After the deploy: `read-pool.sh` with `IO_PRESSURE=0` and
`CAP_PURGE_ROWS=0` (gates 0-3), `dashboard-latency.sh` strict,
`panel-boot.sh`. Threshold unchanged at 50 ms. Results recorded here
once run.

## Known issues carried

The pinned 24 h refresh is the remaining CPU burst that can coincide
with an export on a 1-CPU cgroup; it goes away when the dashboard
reads the hourly rollup (v1.3.42, migration 034). Carried from
v1.3.41.0: `Until` shown as "expired" on imported decisions;
`blocked_requests_24h` mixing; `dashboard/cache_test` timing flake;
the 48 h DB-size reading.
