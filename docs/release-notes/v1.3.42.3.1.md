# v1.3.42.3.1

The tag that ships v1.3.42.3 (deployed on prod on 2026-09-29 19:26
UTC, verified, never tagged) plus one fix found on the prod 7d

readers; this note covers the fix only.

## What ships

`Hist.Percentile` (`backend/internal/db/rollup_read.go`) reports the
5,000 ms edge when the nearest rank falls in the open bucket above
5,000 ms. Until v1.3.42.3 it returned the merged maximum of the
window, which on prod is the lifetime of a long-lived connection:
an `/api/websocket` row of 457,244,622 ms (5.3 days), `/socket.io/`
rows of 80 min, camera-proxy streams of 35 s. Ten of the 169 hours
in the 7d window (2026-09-25 and 26) had more than 1 % of their
requests above 5 s, so ten p99 points sat between 373,940 and
457,244,622 ms and the card's axis scaled to 60,000,000. The rollup's
exact per-group `dur_p99_ms` carries the same maximum for a
websocket-only group, so it was not a way out.

The dashboard card tooltip shows "5,000 ms or more" for that value,
the logs stats card prints "5,000 or more" for a histogram p95 at the
edge, both histogram hints explain the open bucket, and api.md says
the maximum is never reported.

Tests: the existing merge test expects 5,000 (not 9,000) for the
live row above 5 s and checks the maximum is still tracked;
`TestHistOpenBucketEdge` pins p95 in a closed bucket next to p99 in
the open one, every rank in the open bucket, and a rollup-only row
with the prod maximum of 457,244,622 ms, all reporting 5,000.
