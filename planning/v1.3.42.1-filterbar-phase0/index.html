    v1.3.42.1 PHASE 0: one FilterBar, URL state, global search (2026-09-26)¶

    Read-only pass over docs/operations/ux-performance-review.md sections 2, 4 and 8 against the code as it is after v1.3.42.0. Scope is review item 8; items 10 (one decisions table) and 11 (navigation by intent) come later with their own PHASE 0. No backend of logs, rollup or bouncer is touched; the backend changes below are two small read-side ones and are listed as such.

    Vocabulary today, per the review 4.1 and unchanged: q (logs, security) vs search (threats); range (dashboard) vs window (appsec) vs from/to (logs, deliveries); presets 15m-7d (logs), 1h-7d (dashboard), 1h-24h (appsec), 24h-30d (deliveries). No page uses useSearchParams; three pages parse window.location.search once at mount and never write it back.

    Known bugs in this area, in scope:

    1. Logs ignores q, status, path (and ip) from incoming links (Logs.tsx:80-88, read once in the state initialiser, so a second link while already on /logs is ignored too); Dashboard's "top attacking IPs" link /logs?q=<ip> (Dashboard.tsx:597), the 403/429 and 5xx cards (Dashboard.tsx:233-247) and the certificate panel's /logs?source=caddy_error&q=<domain> links (ActiveCertsPanel.tsx:128,191) therefore land on the unfiltered log. Also: q never matches remote_ip except through raw LIKE, and the existing remote_ip param (substring LIKE) is unused by the UI.
    2. Settings loads /api/security/countries, whose rows carry the full cidrs array (country/expander.go:107): about 770 KB on prod for a page that shows counts only.
    3. Closed already and not part of this release: /auth/me per route and the Suspense blank (v1.3.38.5).

    2. Unified model¶

    2.1 Query vocabulary (URL and API use the same names)¶

    Field Values Where it applies
    range 15m, 1h, 6h, 12h, 24h, 7d, 30d (each page mounts the subset its data supports; the server keeps its own param until v1.3.42.2, the client maps) Logs, Dashboard (one range for the page), AppSec, Notifications history
    host_id select fed by /api/hosts once per session (context) Logs, Dashboard, Notifications history
    ip IP, prefix or CIDR Logs (server remote_ip, substring LIKE today; exact-or-CIDR is a v1.3.42.2 backend note), Threats (ip contains), Banned IPs (q), Whitelist (client), Activity (q)
    country ISO code from the data Threats
    scenario scenario or rule name (substring) Threats, Security > Scenarios (client)
    q free text, per-endpoint semantics unchanged Logs, Threats (mapped to search until v1.3.42.2), Banned IPs, Activity, Hosts (client)
    source, status, method, path as today Logs
    origin, scope, type as today Threats, Banned IPs
    tab page's tab id Security, Notifications, Backup, Certificates
    page / offset, limit as each endpoint takes them Logs, Threats, Banned IPs, Activity

    2.2 FilterBar component¶

    frontend/src/components/FilterBar.tsx plus a hook useUrlFilters(schema):

    • The hook owns the state: it reads useSearchParams on mount (with per-field validation and defaults), exposes typed values and a set(partial) that writes the URL with replace for keystrokes and push for range / tab / page changes, so the browser back button walks views, not keystrokes.
    • Text fields debounce 300 ms; every refetch carries an AbortController; the last-known cache (lastKnown.ts) keys on the serialised filter, as Threats does today.
    • Fields are declared per page (fields: ['range', 'host_id', 'q', 'ip', ...] with the allowed range presets); the bar renders only those, in one order everywhere: range, host, enumerations, ip / country / scenario, free text, then the page's own controls.
    • Every IP, domain, scenario and CRS id rendered in a table becomes a link to the page that owns it with the filter pre-filled (/threats?ip=, /logs?ip=&range=24h, /hosts?q=), using the same vocabulary.
    • Tabs move into the URL (?tab=) on the four tabbed pages; reload and shared links land on the right tab.

    Terminology fixes that ride along (UI strings only): the Threats removal button already says "Unban" since v1.3.38.5; "Active bans" (Dashboard card) links to /threats.

    3. Global search¶

    One input in the header. The client classifies the pasted value:

    • IPv4 / IPv6 / CIDR -> ip
    • a hostname (dots, no spaces, not an IP) -> domain
    • crowdsecurity/... or a CRS rule id (6 digits) -> scenario
    • anything else -> q

    On Enter it opens a results panel ("where does it appear") that fans out, read-only, to endpoints that exist today, in parallel with one AbortController:

    Section Call Link it renders
    Decisions (bans) GET /api/threats/decisions?ip= or ?scenario= or ?search= (page 1, per_page 5) /threats?ip=... (or the field used)
    Whitelist GET /api/security/whitelist (client match on the value) /security?tab=whitelist&ip=
    Logs, last 24 h GET /api/logs?remote_ip=&from=now-24h&limit=5 for IPs; ?q= for text; host domain -> ?host_id= after resolving through the hosts cache /logs?ip=&range=24h
    Hosts hosts cache (session context) filtered by domain / target /hosts?q= and /hosts/:id/security
    Scenarios GET /api/security/scenarios (client match) and GET /api/threats/scenarios /security?tab=scenarios&q=
    WAF alerts GET /api/appsec/metrics?window=24h top lists matched on IP / host / rule (client) /appsec?range=24h

    No new aggregate endpoint for v1: every section is one existing GET with the value as its filter, and the counts come from the total each list already returns (logs total_count, threats total). A cross-entity GET /api/search stays a later option if the fan-out (5-6 requests per search) proves too heavy; it is not needed for correctness. Cost per search on prod: decisions (in-memory list), logs 24 h with remote_ip (indexed range plus a filter, sub-second), the rest cached or tiny.

    5. Verification¶

    • Before / after captures with scripts/capture/run-demo.sh on the affected surfaces (logs-browser, dashboard-overview, dashboard-security, security-banned, security-activity, security-scenarios, notifications-deliveries, appsec-metrics, hosts-list-auth-column) plus new captures for the FilterBar on Logs and Threats and for the global search panel; demo only, never a browser against prod.
    • npm run build clean; a unit test for the classifier and for useUrlFilters round-trips (URL -> state -> URL); the API contract unchanged except the cidrs omission, covered by an updated country-expansion-async.sh assertion and a handler test.
    • Manual checklist the operator runs on prod after the deploy:
    • Dashboard "top attacking IPs" -> click an IP -> Logs shows only that IP for 24 h, URL carries ip= and range=24h.
    • Logs: set range 6h, source caddy_error, q=acme; reload; the same view; back button returns to the previous range.
    • Threats: filter by country and scenario; copy the URL into a new tab; same page and filters.
    • Security: open the Activity tab, reload, still on Activity; ?tab=whitelist opens Whitelist.
    • Header search: paste a banned IP -> decisions, logs, whitelist sections with counts; each link lands filtered. Paste a host domain -> hosts and logs. Paste crowdsecurity/http-probing -> decisions and scenarios.
    • Settings: countries block renders counts; the network tab shows /api/security/countries under 20 KB.
    • read-pool.sh gates 0-2 and dashboard-latency.sh as regression (the header search must not add polling).

    6. Release plan¶

    v1.3.42.1 ships the whole of section 2 and 3 in one release, in three commits: (1) useUrlFilters + FilterBar + Logs + Dashboard links (the bug fix), (2) Threats, Security, AppSec, Notifications, Hosts, Backup, Certificates on the bar and tab in the URL, (3) global search + slim countries endpoint + captures + docs. Deploy with the usual OK; no schema, no long write, no bouncer change; the rollup drift window keeps running underneath.
